# DBblue COUNT cache and OFFSET-flip

Two related planner/executor features aimed at deep pagination, as generated by
ERP list views (Odoo's `search_count` followed by `web_search_read`):

1. **COUNT cache** — serve an exact `SELECT count(*) FROM t WHERE p` from a
   session-local cache instead of scanning.
2. **OFFSET-flip** — rewrite a deep `... ORDER BY k LIMIT L OFFSET K` into a
   reversed scan with `OFFSET (N-K-L)`, so the executor reaches the wanted rows
   from the near end of the index.

Both default to **off**. Enable with `dbblue_count_cache` and
`dbblue_offset_flip`.

---

## 1. Why the two are coupled, and why N must be exact

The flip is a coordinate transform: it converts *"K rows from the start"* into
*"N-K-L rows from the end"*. `N` is the bridge between those two coordinate
systems, so an error of `δ` in `N` moves the returned window by exactly `δ`.

This does not degrade gracefully. Measured on a 1000-row table whose cached
count was stale by 3 after three inserts, walking every page:

```
rows emitted by the page walk:  1003   (correct total — nothing looks wrong)
ids NEVER shown on any page:    506 507 508
ids shown TWICE:                1001 1002 1003
```

The total row count is right, no error is raised, and each individual page looks
like a normal page of five rows — while three records silently never appear.
That is why the cache's validity check is load-bearing rather than advisory, and
why a "mostly fresh" count is not good enough.

## 2. Architecture

### 2.1 Cache key — `dbblue_predfingerprint.c`

Key is `(reloid, value-sensitive jumble of the jointree quals)`.

`JumbleExpr(quals, include_consts=true)` extends the standard query-jumble
machinery with an `include_consts` flag (default false), so
`pg_stat_statements` normalisation is unaffected. With the flag set, `Const`
values are folded into the hash, so `state='draft'` and `state='sent'` get
distinct keys.

A qual is rejected outright (fingerprint 0 = uncacheable) when it contains:

| rejected | why |
|---|---|
| `Param` | value supplied at execute time, not visible in the key |
| `SubLink` / `SubPlan` | out of scope |
| **any non-IMMUTABLE function** | see below |
| a system catalog relation | catalog writes bypass the tracking hooks |
| a partitioned table or inheritance parent | writes bump the child's stamp, not the parent's |

The mutable-function rule uses `contain_mutable_functions()`, **not**
`contain_volatile_functions()`. STABLE is not good enough: the fingerprint
hashes the *expression*, so `WHERE owner = current_user` has one fingerprint but
a different answer per role, and `WHERE ts > now() - interval '1 day'` has one
fingerprint but a different answer per day. `contain_mutable_functions()` also
covers `SQLValueFunction`, which is how `current_user` and friends are
represented.

### 2.2 Validity — `dbblue_relmod.c`

The cache is session-local, but a count can be invalidated by *any* backend. The
missing signal is supplied by a fixed-size, direct-mapped table of per-relation
**write stamps** in shared memory (8192 slots, 128 kB).

An entry records the stamp it was captured under, and is served only while a
fresh reading still compares equal — which holds exactly when no transaction, in
this backend or any other, has written to the relation since.

**The stamp is bumped twice.** Both are required:

- **On a transaction's first write to a relation.** Detects writes promptly.
- **Again in `CommitTransaction()`, before `RecordTransactionCommit()`.**
  Write-time alone would miss a transaction that wrote *before* a count was
  captured and committed *after* it — its rows become visible with no
  intervening stamp change. Bumping before the commit record guarantees that any
  backend which can see the new rows also sees a changed stamp.

Bumping on the abort path too is conservative and therefore safe.

Slot collisions **steal** the slot and bump a global eviction epoch which is
folded into every stamp reading. So a collision causes a spurious
*invalidation*, never a spurious *validation* — the failure direction is always
safe.

Writes are hooked at the `tableam.h` wrappers (`table_tuple_insert`,
`_insert_speculative`, `_multi_insert`, `_delete`, `_update`, and
non-transactional truncate) rather than in heapam, so every table AM is covered.
A one-entry per-transaction memo means a bulk load pays a single comparison per
row.

### 2.2.1 The cache is inert during recovery

**WAL redo does not go through the `tableam` wrappers**, so on a hot standby a
relation changes with no stamp movement whatsoever. An entry cached there would
remain "valid" and wrong indefinitely — and because a hit does not renew the
TTL, a polled query shape would never age out of the wrong answer. Demonstrated
on a streaming replica before the guard was added, within one session:

```
1. standby caches                            100
2. same session, after full replay           100   <- wrong
3. same session, feature off (ground truth)   150
```

Both `dbblue_countcache_lookup()` and `dbblue_countcache_insert()` therefore
return early when `RecoveryInProgress()`. Refusing to *populate* as well as to
*serve* means a standby that is later promoted cannot inherit an entry captured
while stamps were not being maintained.

The cost is real: replicas are the read-mostly workload where this feature works
best (96.7 % hit rate at zero writes), and it is switched off there entirely.
Lifting the restriction means bumping stamps from the redo handlers — see §7.4.

### 2.3 Publication is deferred to commit

Counts are **queued**, not published, and reach the cache only at
`XACT_EVENT_COMMIT`, and only if the relation's stamp still matches the value
read at capture. Consequences:

- A count computed inside a transaction that later rolls back is never cached.
- A count overtaken by a concurrent writer between capture and commit is
  discarded rather than published.

A count over a relation **this transaction has written to** is refused outright.
Note the rule is per-relation, not per-transaction: writes to relation `S` cannot
change how many rows of relation `R` are visible. This matters in practice — an
application whose every request also writes a session or audit row (Odoo does)
would otherwise never cache a single count. A temp-table insert in the same
transaction was enough to suppress caching entirely before this was narrowed.

Per-relation membership also subsumes subtransaction rollback without a separate
flag: a relation written by a subtransaction stays in the write set after that
subtransaction aborts, so counts over it stay refused for the rest of the
transaction. Verified for `ROLLBACK`, `ROLLBACK TO SAVEPOINT`, and PL/pgSQL
`EXCEPTION` blocks (which is how Odoo's `cr.savepoint()` behaves).

### 2.4 The flip — `planner.c`

Fires only for a single-relation `SELECT` with non-null quals, a sort clause,
and constant `LIMIT`/`OFFSET`, when a cached `N` exists and `K > N/2`. The plan
is built with flipped sort operators (via each operator's commutator) and
`OFFSET (N-K-L)`, then wrapped in an outer `Sort` that restores the requested
order over the ≤ L returned rows.

## 3. Configuration

| GUC | Default | Notes |
|---|---|---|
| `dbblue_count_cache` | `off` | Serves `count(*)` from cache. |
| `dbblue_offset_flip` | `off` | The rewrite. Depends on the cache — with the cache off there is no `N`, so the flip cannot fire. |
| `dbblue_count_cache_ttl` | `300s` | Memory hygiene, **not** a correctness mechanism. Staleness is prevented by the stamp check. A cache *hit* deliberately does not renew `captured_at`; otherwise a shape polled faster than the TTL would never age out. |

All three are `PGC_USERSET`, so `ALTER SYSTEM SET … ; SELECT pg_reload_conf();`
takes effect on existing connections without an application restart.

> `ALTER SYSTEM` writes `postgresql.auto.conf`, which **overrides**
> `postgresql.conf`. If the feature appears not to fire, check the effective
> value first.

## 4. Correctness

### 4.1 Regression

| | |
|---|---|
| `make check`, defaults | **245/245 pass** |
| `make check`, both GUCs forced on | 244/245 |

The single failure (`create_index`) is a **pre-existing PostgreSQL
plan-dependency, not a cache defect**. With the cache compiled out entirely,
`point_tbl` returns 5 by sequential scan and 4 by GiST index for the identical
query on identical data — the NaN/Inf rows behave differently under the lossy
geometric opclass, and the test's expected output encodes both answers. The
cache faithfully pinned one of them.

The general rule this exposes: **a cached count is sound only where the answer is
plan-independent.**

### 4.2 Vectors covered

Each of these was a real defect found and fixed; all are now verified by probe:

| vector | behaviour |
|---|---|
| Local DML | invalidates immediately |
| **Another backend's** committed DML | invalidates (this is what the shared stamp exists for) |
| Transaction rollback | count never published |
| `ROLLBACK TO SAVEPOINT` / PL/pgSQL `EXCEPTION` | count never published |
| STABLE function in the predicate (`current_user`, `now()`) | not cached; no cross-role or cross-time key collision |
| TTL renewal on hit | removed; hits no longer extend an entry's life |

### 4.3 Differential testing on real data

Against a restored copy of a production Odoo 17 database:

- 29 deep pages sampled across the flip region of a 232,808-row filtered
  `mail_message` list — byte-identical to flip-off.
- A 201-page full walk of a synthetic table — no rows skipped, none duplicated.
- `sale_order` (280,881 matching rows) at K/N = 0.60, 0.80, 0.95, 0.99 —
  md5 of the returned id list identical with the feature on and off.
- A concurrent `INSERT` between the count and the page: the flip correctly
  declined and the page matched ground truth.

## 5. Performance

### 5.1 Synthetic, 5M-row table, `-O2` build with asserts off

```
COUNT(*)      scan 100 ms  ->  cache-served 0.15 ms      (~600x)
```

Flip speedup tracks `K/(N-K-L)`; it does not fire below K/N = 0.5 by design:

| K/N | flip off | flip on | |
|---:|---:|---:|---:|
| 0.52 | 112.6 ms | 97.4 ms | 1.2× |
| 0.70 | 142.9 ms | 61.2 ms | 2.3× |
| 0.90 | 184.6 ms | 20.3 ms | 9.1× |
| 0.99 | 206.7 ms | 2.1 ms | 98× |
| 0.9998 | 205.4 ms | 0.24 ms | 855× |

The large numbers are "jump to the last page", not ordinary paging.

### 5.2 Real Odoo 17 data

`sale_order`, 2.5M rows, 280,881 matching `state='sale'`, last page:

| | off | on | |
|---|---:|---:|---:|
| `search_count` | 286 ms | 0.50 ms | ~575× |
| deep page | 288 ms | 15.9 ms | ~18× |
| **request pair** | **~574 ms** | **~16 ms** | **~35×** |

`sale_order_line`, 5.07M rows: request pair **935 ms → 13 ms**.

Through the real ORM (with a commit between requests, as HTTP requests do):
`search_count` 27.1 ms → 0.90 ms; paginated `search` at OFFSET 26084 flipped
52.2 ms → 9.6 ms, identical ids.

### 5.3 Cost

Within measurement noise. pgbench TPC-B at 8 clients +0.8 %, at 32 clients
−1.1 %; a 5M-row bulk `INSERT … SELECT` −5.4 % (ranges overlap). No contention
blowup at 32 clients despite the single spinlock.

**The write hooks are not GUC-gated**, so this cost is paid even with the feature
off. Per-session gating would be *unsound* — a session with the GUC off would not
bump stamps while another session cached against them. Making it free when
disabled requires a `PGC_POSTMASTER` master switch.

### 5.4 The number that decides deployment

The count and the page are separate transactions, roughly an HTTP round trip
apart, and any commit to that table in the gap invalidates. Measured hit rate
≈ `exp(-r × 0.1s)`:

| writes/s to that table | flip fires | median page |
|---:|---:|---:|
| 0 | 96.7 % | 0.2 ms |
| 1 | 90 % | 0.2 ms |
| 10 | 37 % | 92 ms |
| 30 | 0 % | 94 ms |
| 100 | 0 % | 96 ms |

**So this pays off on large, read-mostly tables** — reporting views, closed-period
journals, catalogs — **and does nothing on write-hot tables** such as
`mail_message`, `stock_move`, or a busy `sale_order`. It degrades to baseline,
never to wrong answers, but do not expect a global speedup.

An UPDATE-only writer at 50/s also drops the hit rate to 0, even though an
`UPDATE` cannot change `count(*)` unless it changes predicate membership. That is
a large, fixable waste — see §7.

## 6. Coverage and known limitations

Gate coverage measured against realistic Odoo list-view SQL — **8 of 12 shapes
eligible**:

**Cached:** bare equality · the `FROM x AS x` self-aliased form Odoo emits ·
ANDed multi-company rule · `IN`-list · `ILIKE '%…%'` search box · literal date
filter · `IS NOT NULL` · numeric comparison.

**Correctly rejected:** `ir.rule` as `IN (SELECT …)` · `ORDER BY` a related field
(forces a join) · relative date `now() - interval` (STABLE).

Known limitations:

1. **No benefit on hot standbys** — the cache is inert during recovery (§2.2.1).
   This is the largest functional gap, because replicas are otherwise the ideal
   workload for it.
2. **Unfiltered list views are never cached.** The gate requires
   `parse->jointree->quals != NULL`, so `SELECT count(*) FROM t` with no `WHERE`
   is excluded — yet that is the most expensive count and the most cacheable.
   Allowing it looks straightforward and sound (no predicate means no mutable
   functions, and the same stamp check applies).
3. **Plan-dependent results** (§4.1) — lossy geometric GiST operators where
   PostgreSQL itself is inconsistent between plans. Verified *not* to affect
   `gin_trgm_ops` `ILIKE` counts, which Odoo relies on heavily: index and
   sequential scans agree.
4. **System catalogs and partitioned/inheritance parents** are excluded, not
   supported.
5. **Write-hot tables** get no benefit (§5.4).
6. **Write-path cost is unconditional** (§5.3).

### 6.1 Not production ready

The core is well validated on a primary, but the following should land before
this is enabled anywhere real:

- **No committed regression tests.** Every correctness vector in §4.2 was
  verified by hand-run probes. Nothing in `make check` would catch a
  regression, and the failure mode is *silently wrong rows*. This is the
  biggest gap.
- **Untested paths:** two-phase commit / prepared transactions, crash
  recovery, `EXEC_BACKEND` shared-memory initialisation (Windows), and slot
  collision behaviour under real multi-relation pressure. A collision bumps a
  *global* epoch, so a busy multi-tenant instance may thrash toward a 0 % hit
  rate — plausible but unmeasured.
- **`PGC_POSTMASTER` master switch** so the write-path cost is genuinely zero
  when the feature is off (§5.3).

## 7. Planned work

### 7.1 Self-counting flip ("tier 2") — removes the write-rate dependency

Put the count in an `OFFSET` subquery so it becomes an **InitPlan**, evaluated
once against the *same* `ActiveSnapshot` as the scan:

```sql
SELECT ... FROM t WHERE p
ORDER BY k ASC                                   -- flipped
LIMIT  LEAST(L, N - K)
OFFSET GREATEST(0, N - K - L)                    -- N = InitPlan count(*)
-- wrapped in a Sort restoring the requested order
```

Exact by construction: no cache, no shared memory, no write-path cost, and
**immune to write rate**. This is a planner rewrite at the same hook the current
flip uses, so the application sends its unchanged plain `OFFSET` query — no ORM
change is required.

Measured via hand-written equivalent SQL, rows identical:
K/N = 0.99 → 213.9 ms → 97.5 ms (2.2×); K/N = 0.90 → 193.2 ms → 108.7 ms (1.8×).
Crossover is around K/N ≈ 0.75, since counting is an index-only scan (~20 ns/row)
while skipping OFFSET rows needs ordered heap access (~43 ns/row).

Key safety property: use the **row estimate** for routing and the InitPlan's
**exact count** for the arithmetic — then a bad estimate costs performance, never
correctness.

Open question: no `RelOptInfo` exists at that hook, so only raw `reltuples` is
available; accurate routing may need a second planner pass.

Since applications already pay for a count on every request, end-to-end on a
write-hot table this is ~306 ms → ~197 ms rather than an added cost.

### 7.2 Column-aware stamps

Split the stamp: INSERT/DELETE/TRUNCATE always bumps; an UPDATE bumps only if
the modified attribute set intersects the predicate's columns. `ExecUpdate`
already computes the modified-column set. This would recover most of the hit
rate on update-heavy tables.

### 7.3 Cache unfiltered counts

See §6 item 2.

### 7.4 Bump stamps during redo, to re-enable the cache on standbys

Teach the heap (and other AM) redo handlers to call
`dbblue_relmod_note_write()` for the relation being replayed, so a hot standby
maintains stamps the same way a primary does. Then the `RecoveryInProgress()`
guard in §2.2.1 can be lifted and replicas get the optimisation back.

Points needing care: redo has no relcache entry, only a `RelFileLocator`, so the
relation OID must be recovered from it (or the stamp keyed on the locator
instead of the OID); and the stamp must be bumped before the replayed changes
become visible to queries on the standby, mirroring the pre-commit ordering
used on the primary.

## 8. Testing

```bash
make check                                                # defaults (feature off)
make check EXTRA_REGRESS_OPTS="--temp-config=on.conf"     # both GUCs forced on
```

where `on.conf` contains `dbblue_count_cache = on` and `dbblue_offset_flip = on`.

Observability: the serve and flip paths emit `DEBUG1` lines, so
`log_min_messages = debug1` plus `grep dbblue` on the server log shows exactly
what fired:

```
FLIP       rel=sale_order  N=2504699 K=2504640 L=80 new_off=0
CACHE HIT  rel=sale_order  count=2504699 hits=9
```

`hits=N` is how many times an entry has been reused. Silence means either the
query did not qualify or the cache was invalidated by a write.

## 9. Operational notes

- **Building for an Odoo test:** a top-level `make install` does **not** install
  `contrib`, so `pg_trgm` will be missing and Odoo's trigram index creations will
  fail on restore. Run `make -C contrib install`.
- **Restoring a production database:** always run `odoo-bin neutralize` **before**
  starting Odoo against the copy, and pass `--max-cron-threads=0`. `workers = 0`
  does *not* disable cron — Odoo runs cron in threads in that mode.
- **Odoo timestamps are naive UTC.** Comparing `ir_cron.lastcall` or
  `create_date` against `now()` under a non-UTC `TimeZone` silently shifts the
  window. Compare against `(now() AT TIME ZONE 'UTC')`.
